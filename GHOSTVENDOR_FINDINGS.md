## What Failed
The `create_payment_intent` function in `src/app/clients/stripe.py` had no timeout on the HTTP request, causing indefinite hangs. It did not check `response.status_code` before parsing JSON, so 429/502/503 errors triggered JSON parsing of error bodies (often malformed or empty), leading to `KeyError` when callers accessed `result["id"]`/`result["status"]`. All exceptions propagated unhandled, resulting in HTTP 500.

## Fix Applied
- Added `timeout=10` to `requests.post()`.
- Wrapped the call in a retry loop (max 2 attempts) with 1-second sleep on transient status codes 429, 502, 503.
- Added explicit `status_code` checks: return structured error dicts for HTTP >=400.
- Wrapped `response.json()` in try/except for `ValueError` (malformed JSON) and generic `Exception` (empty response).
- All failure paths return a structured error dict with `error` and `message` keys instead of raising.

## Why This Strategy
`timeout_with_retry` directly addresses the root causes: missing timeout, missing retry on transient codes, unguarded JSON parsing, and unguarded empty responses. Structured error returns allow callers to degrade gracefully (check for `"error"` key) instead of crashing with KeyError.
- **SendGrid**: fix(sendgrid): add timeout, retry, and error propagation to send_email

## What Failed
The `send_email` function in `src/app/clients/sendgrid.py` called `requests.post()` without a timeout, causing indefinite hangs on slow vendor responses. It returned the raw HTTP status code without checking for 4xx/5xx errors. The notify route (`src/app/routes/notify.py`) wrapped whatever code was returned into a 200 OK response, so vendor 429 and 502 errors were silently swallowed and presented as success. No retry logic existed for transient 429/502/503 errors.

## Fix Applied
- Added `timeout=10` to the `requests.post()` call.
- Wrapped the call in a try/except block catching `requests.exceptions.Timeout` and `requests.exceptions.RequestException`.
- On timeout or request exception, return a structured error dict (e.g., `{"error": "timeout", "message": "..."}`).
- On transient status codes (429, 502, 503), retry once after a 1-second sleep; if the retry also fails, return a structured error dict.
- Updated the notify route to check if the returned value is an error dict and, if so, return HTTP 503 with the error details instead of a false 200 OK.

## Why This Strategy
The `timeout_with_retry` strategy directly addresses the identified patterns: `missing_timeout`, `silent_failure_swallowing`, `no_error_propagation`, and `missing_retry`. A 10-second timeout prevents hangs; structured error returns allow callers to distinguish success from failure; a single retry with backoff handles transient rate limits and gateway errors without adding the complexity of a circuit breaker (which is optional at Criticality 30).
