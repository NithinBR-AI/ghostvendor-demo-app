- **Stripe**: fix(stripe): add timeout and retry logic to create_payment_intent

## What Failed
The `create_payment_intent` function in `src/app/clients/stripe.py` made raw `requests.post()` calls with no timeout, causing indefinite hangs. It did not check `response.status_code` before calling `response.json()`, so 429/502/503 errors proceeded to JSON parsing, likely causing `KeyError` downstream when accessing `result['id']`. No retry logic existed for transient errors.

## Fix Applied
- Added `timeout=10` to the HTTP call.
- Wrapped the call in a try/except block catching `Timeout` and `RequestException`.
- Added retry logic: on transient status codes (429, 502, 503) or caught exceptions, sleep 1 second and retry once (max 2 attempts total).
- On final failure, return a structured error dict (e.g., `{"error": "timeout", "message": "..."}`) instead of raising.
- Added required imports: `time`, `requests.exceptions.Timeout`, `requests.exceptions.RequestException`.

## Why This Strategy
The `timeout_with_retry` strategy directly addresses the root cause: missing timeouts cause hangs, missing status-code checks cause parse errors on error bodies, and missing retries leave transient failures unhandled. Returning structured error dicts allows callers (e.g., `charge.py`) to degrade gracefully instead of crashing with HTTP 500.
- **SendGrid**: fix(sendgrid): add timeout handling and retry logic for transient errors in notify route

## What Failed
The notify route called `sendgrid.send_email()` without any timeout, retry, or error handling. SendGrid 502/429 responses were swallowed and returned as HTTP 200 with `status: sent`. Network timeouts caused unbounded hangs.

## Fix Applied
- Added imports for `Timeout`, `RequestException` from `requests.exceptions` and `time` for sleep.
- Wrapped the `send_email` call in a retry loop (max 1 retry).
- On `Timeout` or `RequestException`, sleep 1s and retry once; on final failure return structured error with HTTP 504.
- On transient vendor codes (429, 502, 503), sleep 1s and retry once; on final failure return structured error with the vendor's HTTP code.
- On success (non-retry code), return the original success payload.

## Why This Strategy
`timeout_with_retry` matches the criticality score (30): email is asynchronous and non-blocking, so we add resilience (timeout awareness, one retry for transient errors, proper error propagation) without aggressive circuit breaking. The fix stays in the route layer, requiring no changes to the SendGrid client.
