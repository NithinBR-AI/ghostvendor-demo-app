## Root Cause Diagnoses
- **Stripe** (`src/app/clients/stripe.py` → `create_payment_intent`): timeout_with_retry — The Stripe client's `create_payment_intent` function (src/app/clients/stripe.py:22-45) makes a raw `requests.post` call with no timeout parameter, causing the app to hang indefinitely on slow vendor responses (timeout, malformed_json, empty_response scenarios). It does not inspect `response.status_code`, so vendor errors like 502 (502_burst) and 429 (429_rate_limit) are passed to `response.json()` which either raises JSONDecodeError on the HTML error page or returns an error object; the charge route (`charge()` in src/app/routes/charge.py:18-30) then accesses `result["id"]` causing a KeyError that Flask converts to HTTP 500. No retry logic exists for transient 429/502 errors, no circuit breaker prevents repeated calls to a failing vendor, and `response.json()` is called without try/except leaving malformed or empty JSON unhandled.
- **SendGrid** (`src/app/clients/sendgrid.py` → `send_email`): timeout_with_retry — The send_email function in src/app/clients/sendgrid.py calls requests.post without a timeout parameter (line 27-36), causing the HTTP request to hang indefinitely when SendGrid is slow, returns 502, or rate-limits with 429. All three chaos modes manifest as requests.exceptions.Timeout because the underlying TCP connection never times out. Additionally, there is no retry logic for transient 429/502 responses, so even if a timeout were added, a single transient failure would still cause full request failure.

Stripe calls hung indefinitely with no timeout and crashed on transient errors because the caller accessed result fields without checking for errors.

## Why This Strategy

## What Failed
