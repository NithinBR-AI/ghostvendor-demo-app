## Root Cause Diagnoses
- **Stripe** (`src/app/clients/stripe.py` → `create_payment_intent`): timeout_with_retry — The create_payment_intent function in src/app/clients/stripe.py makes a requests.post call with no timeout parameter, causing all five chaos modes (timeout, 502_burst, 429_rate_limit, malformed_json, empty_response) to hang indefinitely until the harness kills the request. It also lacks retry logic for transient 429/502 errors, calls response.json() without try/except (crashing on malformed JSON), assumes a non-empty response body before parsing, and has no circuit breaker to stop hammering a failing Stripe endpoint.
- **Stripe** (`src/app/routes/charge.py` → `charge`): graceful_degradation — The charge route handler in src/app/routes/charge.py calls stripe.create_payment_intent and immediately accesses result["id"] and result["status"] without any error handling. When the client raises requests.exceptions.Timeout (or any other exception), the exception propagates unhandled, causing Flask to return a 500 Internal Server Error instead of a structured error response to the caller.
- **SendGrid** (`src/app/clients/sendgrid.py` → `send_email`): timeout_with_retry — The send_email function in src/app/clients/sendgrid.py calls requests.post with no timeout parameter, causing indefinite hangs when SendGrid is slow (timeout mode). It has no retry logic for transient errors like 502 or 429 (502_burst mode), and no circuit breaker to stop repeated calls to a failing vendor. The function returns the raw HTTP status code without validating success, deferring all error handling to the caller.
- **SendGrid** (`src/app/routes/notify.py` → `notify`): graceful_degradation — The notify route in src/app/routes/notify.py calls sendgrid.send_email and unconditionally returns 200 OK with {"status": "sent", "code": code} regardless of whether SendGrid returned 202 (success) or an error code like 502, 429, or 500. It never inspects the returned status code, so upstream callers receive a false success signal when the email actually failed.

## Attempted Patches
- **Stripe**: fix(stripe): add timeout, retry, and error handling to create_payment_intent

## What Failed
Stripe payment intent creation hung indefinitely on timeouts, 502 bursts, and rate limits with no retry logic or error recovery.
## Fix Applied
Added a 5-second timeout, one retry on transient 429/502/503 errors with a 1-second sleep, and structured error dicts for timeouts, request failures, and malformed JSON.
## Why This Strategy
Timeout with retry protects revenue-critical payment flows by failing fast on persistent errors while recovering from transient blips without blocking the caller.

## Fix Applied

## Why This Strategy
Graceful degradation ensures upstream systems always receive an explicit 5xx with a predictable error shape so compensating transactions can fire immediately.
- **SendGrid**: fix(sendgrid): add timeout and retry logic to send_email

## What Failed
The send_email function had no timeout, causing indefinite hangs when SendGrid was slow. It also lacked retry logic for transient errors like 502 or 429.

## Fix Applied
Added a 10-second timeout to the HTTP call and a single retry with a 1-second sleep for transient status codes (429, 502, 503) and timeout exceptions. Returns a structured error dict on final failure.

## Why This Strategy
Timeout with retry is appropriate for a criticality score of 30, balancing reliability with conservative resource usage. It prevents hangs and handles transient failures without aggressive retry storms.
- **SendGrid**: fix(sendgrid): propagate SendGrid errors instead of masking them

## What Failed

## Fix Applied
Added graceful degradation: inspect the returned status code and return 503 on non-2xx or exceptions, logging a warning.
## Why This Strategy
Graceful degradation ensures upstream alerting and retry logic receive accurate failure signals without breaking the response contract.
