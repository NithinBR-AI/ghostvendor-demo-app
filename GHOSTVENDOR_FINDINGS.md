## Root Cause Diagnoses
- **Stripe** (`src/app/clients/stripe.py` → `create_payment_intent`): timeout_with_retry — The `create_payment_intent` function in `src/app/clients/stripe.py` makes a raw `requests.post` call with no timeout parameter, causing the timeout chaos mode to hang indefinitely until the test harness kills it (observed as `requests.exceptions.Timeout`). It lacks any retry logic, so transient 502 and 429 responses from Stripe are not retried and instead propagate as unhandled failures (observed as HTTP 500 in 502_burst and 429_rate_limit modes). The function calls `response.json()` without a try/except guard, so malformed JSON from the vendor would raise `JSONDecodeError` (simulated in malformed_json mode, though the harness timeout triggered first). It also assumes the response body is non-empty; an empty response would cause `json()` to fail (simulated in empty_response mode, again preempted by timeout). Finally, there is no circuit breaker, so repeated failures during a burst or rate-limit event keep hammering the dead vendor.
- **SendGrid** (`src/app/clients/sendgrid.py` → `send_email`): timeout_with_retry — The send_email function in src/app/clients/sendgrid.py makes a raw requests.post() call with no timeout parameter, no retry logic for transient errors (429, 502), and no circuit breaker. When SendGrid returns 502 or 429, the client simply returns the status code without any resilience handling, causing the caller to receive error codes that it then mishandles.
- **SendGrid** (`src/app/routes/notify.py` → `notify`): graceful_degradation — The notify function in src/app/routes/notify.py calls sendgrid.send_email() and unconditionally returns jsonify({'status': 'sent', 'code': code}) with HTTP 200, even when SendGrid returns error codes like 502 or 429. The route never inspects the returned status code to distinguish success from vendor failure, silently swallowing errors and reporting them as success.

## Attempted Patches
- **Stripe**: fix(stripe): add timeout and retry to create_payment_intent

## What Failed
Stripe payment intent creation hung indefinitely without a timeout and propagated transient 429/502/503 errors without retry.
## Fix Applied
Added a 10-second timeout to the requests call and a single retry with a 1-second sleep on 429, 502, or 503 responses.
## Why This Strategy
Timeout prevents hanging and retry handles transient failures, balancing resilience with minimal latency impact for this high-criticality vendor.
- **SendGrid**: fix(sendgrid): add timeout and retry for transient failures in send_email

## What Failed
SendGrid client had no timeout or retry logic, causing callers to receive raw 429/502/503 status codes with no resilience.
## Fix Applied
Added a 10-second timeout on the requests call and a single retry with 1-second sleep for HTTP 429, 502, and 503 responses.
## Why This Strategy
Timeout prevents indefinite hangs and retry handles transient server errors, matching the moderate criticality requirement for standard resilience.
- **SendGrid**: fix(sendgrid): propagate SendGrid failures as 503 instead of masking as 200

## What Failed
The notify route unconditionally returned HTTP 200 with status 'sent' even when SendGrid returned error codes like 502 or 429, silently swallowing failures.
## Fix Applied
Added graceful degradation: the route now inspects the return value from sendgrid.send_email() and returns HTTP 503 with an error payload when the vendor signals failure or returns a non-2xx status code.
## Why This Strategy
Graceful degradation is appropriate because SendGrid is criticality 30 and upstream callers must see real failures to trigger fallback logic rather than receiving false success responses.
