## Root Cause Diagnoses
- **Stripe** (`src/app/clients/stripe.py` → `create_payment_intent`): timeout_with_retry — The `create_payment_intent` function in `src/app/clients/stripe.py` calls `requests.post` with no timeout parameter, causing the timeout, malformed_json, and empty_response chaos modes to hang until the underlying library times out (observed as `requests.exceptions.Timeout`). It performs no retry on transient 429 or 5xx responses, so the 429_rate_limit and 502_burst scenarios propagate as unhandled exceptions that Flask converts to HTTP 500. It calls `response.json()` without a try/except block, so malformed JSON from the vendor crashes the parser. It assumes the response body is non-empty, so an empty response crashes. No circuit breaker tracks consecutive failures, so a degraded Stripe endpoint continues to receive traffic.
- **SendGrid** (`src/app/clients/sendgrid.py` → `send_email`): timeout_with_retry — The send_email() function in src/app/clients/sendgrid.py calls requests.post() with no timeout parameter, causing the timeout chaos mode to raise an uncaught requests.exceptions.Timeout. It also lacks any retry logic for transient vendor errors (429 rate limit, 502 burst) and has no circuit breaker to stop hammering a failing vendor. The function simply returns response.status_code (502, 429, or 202) to the caller without interpretation.
- **SendGrid** (`src/app/routes/notify.py` → `notify`): graceful_degradation — The notify() route in src/app/routes/notify.py calls sendgrid.send_email() and unconditionally returns jsonify({'status': 'sent', 'code': code}) with HTTP 200, even when the client returns vendor error codes 502 or 429. The route never inspects the returned status code to distinguish success (202) from failure, so vendor errors are silently swallowed inside a 2xx response body.

## Attempted Patches
- **Stripe**: fix(stripe): add timeout and retry to create_payment_intent

## What Failed
Stripe payment intent creation hung indefinitely on timeouts and crashed on transient 429/502/503 errors because no timeout or retry logic existed.
## Fix Applied
Added a 10-second timeout on the requests call, immediate error return on timeout, and a single retry with 1-second sleep for 429, 502, and 503 status codes.
## Why This Strategy
Timeout with retry is the lightest-weight resilience pattern that addresses the observed failures without adding stateful circuit breaker complexity to a critical payment path.
- **SendGrid**: fix(sendgrid): add timeout and retry logic to send_email

## What Failed
SendGrid requests had no timeout and no retry logic, causing uncaught Timeout exceptions and propagating transient HTTP errors (429, 502, 503) directly to callers.

## Fix Applied
Added a 10-second timeout on the requests.post call and a single retry with a 1-second sleep for transient status codes 429, 502, and 503. Timeout exceptions return an error dict instead of raising.

## Why This Strategy
Timeout with retry is appropriate for a moderate-criticality vendor like SendGrid. It prevents indefinite hangs while gracefully handling transient failures without the complexity of a full circuit breaker.
- **SendGrid**: fix(sendgrid): propagate vendor errors as HTTP 503 in notify route

## What Failed
The notify route returned HTTP 200 with status: sent even when SendGrid responded with 502 or 429, silently swallowing failures.
## Fix Applied
Added graceful degradation: the route now inspects the SendGrid client return value and returns HTTP 503 with an error body on any non-2xx status or error dict.
## Why This Strategy
Graceful degradation ensures callers receive a clear failure signal instead of a misleading success response, which is critical for a vendor with criticality score 30.
