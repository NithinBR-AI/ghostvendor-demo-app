## What Failed
The Stripe client's `create_payment_intent` function called `requests.post` with no timeout, causing indefinite hangs when Stripe is slow or unresponsive. All six chaos scenarios (timeout, 502_burst, 429_rate_limit, malformed_json) manifested as `requests.exceptions.Timeout` because the vendor simulator delays responses for error modes. The function also called `response.json()` without try/except, had no retry logic for transient 429/502/503 errors, and no circuit breaker. The route handler in `src/app/routes/charge.py` did not catch exceptions, so any failure propagated as an unhandled 500.

## Fix Applied
- Added `timeout=10` to the HTTP request
- Wrapped the call in a retry loop (max 2 attempts) with 1-second sleep between attempts
- Retry on transient status codes 429, 502, 503
- Catch `Timeout` and `RequestException`, return structured error dicts
- Catch `ValueError` from `response.json()` for malformed JSON
- Patched the caller `charge.py` to check for `"error"` in result before accessing `result["id"]` and `result["status"]`, returning a 503 with error message on failure

## Why This Strategy
The `timeout_with_retry` strategy directly addresses the root cause: missing timeout and missing retry. A 10-second timeout bounds the wait, while a single retry on transient codes handles temporary vendor blips. Structured error dicts allow the caller to handle failures gracefully without exceptions. The caller patch prevents KeyError crashes when the vendor returns an error dict instead of a success response.
