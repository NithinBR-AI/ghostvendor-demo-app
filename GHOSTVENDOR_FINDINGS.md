## Root Cause Diagnoses
- **Stripe** (`src/app/clients/stripe.py` → `create_payment_intent`): timeout_with_retry — The `create_payment_intent` function in `src/app/clients/stripe.py` makes a raw `requests.post` call with no timeout parameter, causing indefinite hangs when Stripe is slow (timeout scenario). It lacks retry logic for transient errors — 429 rate limits and 502 bursts propagate immediately as failures. No circuit breaker exists to stop hammering a failing vendor. The function calls `response.json()` without try/except, so malformed JSON or empty responses from Stripe raise uncaught `JSONDecodeError` exceptions. All these vulnerabilities cause unhandled exceptions that bubble up to the route handler.
- **Stripe** (`src/app/routes/charge.py` → `charge`): graceful_degradation — The `charge` route handler in `src/app/routes/charge.py` calls `stripe.create_payment_intent` and immediately accesses `result["id"]` and `result["status"]` without verifying the Stripe call succeeded. When Stripe returns 429 or 502 with an error JSON body, the client returns that error dict (lacking "id"/"status" keys), causing a KeyError that becomes HTTP 500. When the client raises exceptions (Timeout, JSONDecodeError), they propagate unhandled, also becoming HTTP 500. The route never inspects the client result for error indicators or catches exceptions.
- **SendGrid** (`src/app/clients/sendgrid.py` → `send_email`): timeout_with_retry — The send_email() function in src/app/clients/sendgrid.py calls requests.post() with no timeout parameter, causing the timeout chaos mode to raise an uncaught requests.exceptions.Timeout. It also lacks any retry logic for transient HTTP codes (429 rate limit, 502 burst) and has no circuit breaker to stop hammering a failing vendor. The function simply returns response.status_code (including 429/502) to the caller without interpretation.
- **SendGrid** (`src/app/routes/notify.py` → `notify`): graceful_degradation — The notify() route in src/app/routes/notify.py calls sendgrid.send_email() and receives the raw HTTP status code (including 429 and 502), but unconditionally returns jsonify({'status': 'sent', 'code': code}) with a 200 OK HTTP response. This masks vendor failures as successes — the 429_rate_limit and 502_burst scenarios both returned HTTP 200 with the error code embedded in the JSON body.

## Attempted Patches
- **Stripe**: fix(stripe): add timeout and retry to create_payment_intent

## What Failed
Stripe payment intent creation had no timeout, causing indefinite hangs, and no retry logic for transient 429/502/503 errors.
## Fix Applied
Added a 10-second timeout and a single retry with 1-second sleep on transient HTTP errors or request exceptions.
## Why This Strategy
Timeout with retry prevents hanging and handles transient failures gracefully while keeping latency predictable for this critical payment path.
- **Stripe**: fix(stripe): gracefully degrade charge route on vendor failures

## What Failed
The charge route accessed result["id"] and result["status"] without checking for errors, causing KeyError and HTTP 500 when Stripe returned error dicts or exceptions.
## Fix Applied
Wrapped the Stripe call in try/except, checked for error dicts from the patched client, and validated the response shape before accessing keys, returning 503 on any failure.
## Why This Strategy
Graceful degradation ensures the route never returns 500 for vendor failures, mapping all error conditions to a semantic 503 with structured error JSON.
- **SendGrid**: fix(sendgrid): add timeout and retry logic to send_email

## What Failed
SendGrid API calls had no timeout, causing uncaught Timeout exceptions, and no retry logic for transient HTTP errors (429, 502, 503).
## Fix Applied
Added a 30-second read timeout and a retry loop with up to 3 attempts, sleeping 1 second between retries on transient status codes or request exceptions.
## Why This Strategy
Timeout with retry is appropriate for moderate-criticality vendors to handle transient failures without blocking indefinitely or hammering the service.
- **SendGrid**: fix(sendgrid): propagate vendor errors as HTTP 503 in notify route

## What Failed
The notify route swallowed SendGrid errors by returning HTTP 200 with the raw status code in the body, masking 429 and 502 failures as successes.
## Fix Applied
Added graceful degradation checks: if the client returns an error dict or a 4xx/5xx status code, the route now returns HTTP 503 with the error details.
## Why This Strategy
Graceful degradation ensures vendor failures are surfaced to callers with correct HTTP semantics, preventing silent data loss for a criticality-30 service.
