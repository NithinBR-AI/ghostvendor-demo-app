## Root Cause Diagnoses
- **Stripe** (`src\app\clients\stripe.py` → `create_payment_intent`): timeout_with_retry — The `create_payment_intent` function in `src/app/clients/stripe.py` calls `requests.post` with no `timeout` parameter, causing indefinite hangs on slow vendor responses — the timeout, 502_burst, 429_rate_limit, and empty_response chaos modes all manifest as uncaught `requests.exceptions.Timeout`. It lacks any retry logic for transient HTTP errors (429, 5xx), has no circuit breaker to stop hammering a failing vendor, calls `response.json()` without `try/except` so malformed JSON crashes the handler (malformed_json mode), and assumes the response body is non-empty so empty responses also crash parsing.
- **Stripe** (`src\app\routes\charge.py` → `charge`): graceful_degradation — The `charge` route handler in `src/app/routes/charge.py` calls `stripe.create_payment_intent` and unconditionally accesses `result["id"]` and `result["status"]` assuming success; any exception from the client (timeout, JSON decode error, KeyError on error responses) propagates unhandled, causing Flask to return a generic 500 instead of a semantic error code (e.g., 502/503/429) that would allow callers to react appropriately.
- **SendGrid** (`src/app/clients/sendgrid.py` → `send_email`): timeout_with_retry — The send_email() function in src/app/clients/sendgrid.py calls requests.post() without a timeout parameter, causing the request to hang indefinitely when SendGrid is slow or unresponsive (observed as Timeout exceptions in all three chaos modes). It also lacks any retry logic for transient errors such as 429 rate limits or 502 bad gateway bursts, and has no circuit breaker to stop repeated calls to a failing vendor.
- **SendGrid** (`src/app/routes/notify.py` → `notify`): graceful_degradation — The notify() route handler in src/app/routes/notify.py calls sendgrid.send_email() and unconditionally returns jsonify({'status': 'sent', 'code': code}) with HTTP 200, even when SendGrid returns error codes like 502 or 429. The route never inspects the returned status code to determine if the email was actually accepted.

## Attempted Patches
- **Stripe**: fix(stripe): add timeout and retry to create_payment_intent

## What Failed
Stripe payment intent creation had no timeout, causing indefinite hangs, and no retry logic for transient HTTP errors.
## Fix Applied
Added a 10-second timeout on the requests call and a single retry with 1-second sleep on 429, 502, or 503 status codes.
## Why This Strategy
Timeout prevents resource exhaustion from slow vendor responses, and a single retry handles transient failures without overwhelming the vendor.
- **Stripe**: fix(stripe): gracefully degrade charge route on vendor failure

## What Failed
The charge route assumed Stripe always returned a valid payment intent dict, causing unhandled exceptions and generic 500 errors on any vendor failure.
## Fix Applied
Wrapped the Stripe call in try/except and check for error dicts returned by the patched client, returning 503 with a structured error on any failure.
## Why This Strategy
Graceful degradation preserves caller semantics by surfacing vendor failures as proper HTTP error codes instead of crashing, allowing upstream resilience policies to react appropriately.

## What Failed

## Fix Applied
Added a 10-second timeout to the requests.post call and a single retry with a 1-second sleep on status codes 429, 502, or 503.
## Why This Strategy
Timeout prevents resource exhaustion from hanging calls, and a single retry handles brief rate-limit or gateway bursts without excessive load.
- **SendGrid**: fix(sendgrid): propagate SendGrid failures as 503 in notify route

## What Failed
The notify route always returned HTTP 200 even when SendGrid returned error status codes or an error dict, causing silent failures.
## Fix Applied
Added graceful degradation: the route now inspects the SendGrid result for error dicts and non-2xx status codes, returning 503 with an error payload on failure.
## Why This Strategy
Graceful degradation ensures upstream callers receive accurate failure signals so they can retry, alert, or fall back appropriately.
